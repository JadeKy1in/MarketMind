# S8 设计（第一部分）：大行情警报框架

> 规格来源：`docs/SPEC_v3.md` §1、§6.3、§10、§13（S8：Playground 接回 + 顾问 + 大行情警报）。日期：2026-09-28；警报判定 2026-09-29 按所有人决定改版（趋势主干 + 附注）。

## 范围

- **做**：警报的代码判定（2026-09-29 改版：趋势状态机为主干，顾问与证据为附注）；观察模式（S7 之前）；警报记录进账本；所有人对警报的回应（接受 / 拒绝）与"放弃的价值"；推送层（与渠道无关，支持在中国可用的微信 / 企业微信 / 飞书推送）；仪表盘"警报"页。
- **不做**：顾问评选（S7，晋升评审）；Playground 接回；自动下单（L1/L2 禁止）。
- 所有人决定（2026-09-28）：S7 之前用**观察模式**；推送渠道要在中国能用（所有人以后回国，倾向微信）。

## 警报判定（所有人 2026-09-29 决定改版，取代原"三条件同时满足"）

**主干 = 趋势状态机。** 警报候选 = 所有人能执行的标的，今天的趋势状态发生切换：

| 类型 | 切换 | 方向 |
|---|---|---|
| 入场警报 | CASH / WATCH / EXIT → TREND | 做多 |
| 离场警报 | TREND → CASH / WATCH / EXIT | 离场（看空方向） |

- 状态和切换来自**可插拔的趋势信号源**（`alerts/trend_source.py`），默认读每日状态机文件 `data/trend/<纽约日期>.json`：文件里有精简版（lean）标的清单就用精简版，否则用全池；切换以文件里的 `changes`（与每个标的上一份记录比较）为准。只读当天的文件，缺失就当天没有警报（报告写明原因），不拿旧文件顶替。
- **只列所有人能执行的工具**（Robinhood 可交易、非期权）；不能执行的切换列在报告 `skipped` 里。
- 顾问意见（原条件 A）和证据层背离（原条件 B）改为**附注**：不是必要条件，也**不拦截**警报。

**顾问附注（按资产组投票）**
- 投票者：`data/advisors.json` 里的顾问——长期名册影子**和 Playground 候选**（`playground:` 编号，组别记为 `playground`）都算；名单为空时，全部在册上线影子 + 账本里出现过的 Playground 候选代投（`voter_basis = stand_in`）。
- 票按**资产组**聚合（`alerts/asset_groups.py::ASSET_GROUPS`，一张表）：例如加密（BTC-USD、ETH-USD、SOL-USD、IBIT…）、贵金属（GLD、SLV、GC=F、SI=F、GDX…）、美股指数（SPY、QQQ、IWM、DIA、ES=F、NQ=F…）、长端利率（TLT、IEF、ZN=F…）、能源（USO、XLE、CL=F…）、行业 ETF 归入各自行业组；表里没有的标的自成一组（精确代码）。反向 / 杠杆产品和收益率指数不入表（方向相反或失真）。
- 每个投票者在每个资产组只算近 5 天内最新的一条决策；**持有期 < 10 个交易日的决策不投票**。
- 同向 = 入场警报看做多、离场警报看做空。

| 附注 | 判定 |
|---|---|
| 顾问支持 `supported` | 同向 ≥ 2 票，来自 ≥ 2 个名册组（Playground 算一个组），且反向票 ≤ 同向票的一半 |
| 否决标记 `vetoed` | 投票者中**过半**（严格多于一半）方向相反——只显示警示，不拦截 |
| 支持不足 `weak` | 有人投票但不满足以上两条 |
| 无顾问意见 `no_votes` | 该资产组无人投票 |

**证据附注**：近 5 天证据层背离记录中，同一资产组、方向与警报相同的列为支持说明；方向相反的单列（`evidence_against`）。

- **接近触发**改为：可执行、状态为 WATCH（两条过滤都满足，只差 55 日突破）的标的，只进报告和仪表盘。
- **去重**：同一趋势事件（标的 + 类型 + 入场信号日 / 离场数据日）只警报一次（查近 14 天的警报报告和账本）；新的一轮入场是新事件，照常警报。
- **周末**：周末运行在趋势步骤之后也评估警报，只看加密标的（纯代码，不调用 LLM）。

## 账本

- 每条**入场**警报（观察或正式）记一条：`source_type=alert`，`source_id=alert:observe` 或 `alert:live`；做多，下一个开盘价入场，持有 20 个交易日，仓位 $1,000（观察用固定名义金额），确信度 0.6，可证伪条件 = 趋势状态机的吊灯止损价（收盘跌破即判错），`meta` 里存趋势来源、资产组、附注（`status`、同向 / 反向票、证据）和去重键。
- **离场**警报只进报告，不记账本（所有人只做多，离场不是一笔可结算的新仓位）。
- 所有人回应：`python -m marketmind.alerts ack <警报编号> accept|reject [--note ...]`，写入 `data/alerts/responses.jsonl`。被拒绝的警报就是 SPEC §6.3 的 missed_path：它的账本记录照常结算，仪表盘把"拒绝后的结果"单列出来，量化"放弃"的价值。

## 推送（`marketmind/alerts/notify.py`）

- 渠道由环境变量决定，设了哪个就用哪个（可以同时设多个）：Server酱（推到微信）、PushPlus（推到微信）、企业微信群机器人、飞书自定义机器人。具体接口格式见代码注释里的文档链接与核对日期。
- 密钥只从环境变量读，放在 URL 里的也不写日志；发送失败只记录渠道名和 HTTP 状态。
- `python -m marketmind.alerts test-notify` 发一条测试消息，确认渠道可用。
- **一次运行只发一条消息**：本次所有警报合并（离场在前），每条写标的、入场 / 离场、状态切换、收盘与趋势止损、顾问附注（否决标记单独一行）、证据摘要、账本编号，最后是"系统不下单，由你决定"。
- **优先级**：警报以 `send(..., priority=True)` 发送。企业微信对优先消息加 `@all`（`text.mentioned_list = ["@all"]`，官方文档 2026-09-29 核对）；Server酱、PushPlus 没有优先级字段，飞书的 @所有人 需要群开启权限、文档未说明未开启时是否拒收，所以这三个渠道不变。
- 顺序：每日运行里警报在日报推送之前；观察名单的触发推送在主管线内（早于影子交卷和趋势步骤），目前排在警报之前——Server酱 免费版每天 5 条，若以后观察名单推送多，可能占满额度，见"未决"。

## 运行

- 每日运行：持仓巡检 → 晋升评审 → 趋势步骤 → **警报** → 日报；周末运行：趋势步骤（加密）→ **警报（加密）**。也可 `python -m marketmind.alerts run [--crypto-only]`。
- 报告写 `data/alerts/<UTC 日期>.json`：`mode`、`live_switch`、`trend_source`（来源名、数据日期、清单、是否可用及原因）、`voter_basis`、`fired`、`near_misses`（WATCH）、`duplicates`、`skipped`、`pushed`。为兼容仪表盘第一版的 A/B/C 列，每行仍带 `a_ok`（= 顾问支持）、`b_ok`（= 有同向证据）、`c_ok`（= 趋势切换）。

## 所有人开关（`alerts/config.py`）

- **正式模式（推送）只由所有人明确打开**：`LIVE = False`（默认），或环境变量 `MARKETMIND_ALERTS_LIVE=1`。顾问人数不再决定模式（取代 2026-09-29 红队修复里"顾问能满足条件 A 才转正式"的规则；那条修复的本意——不在条件不具备时贸然推送——由人工开关保留）。观察模式照旧：计算、写报告、入场警报记账本（`alert:observe`），不推送。
- **换趋势信号源**：`TREND_SOURCE`（默认 `daily_state_machine:six`：日线状态机、只看 SPY、QQQ、GLD、TLT、BTC-USD、ETH-USD，所有人 2026-09-29 按三次回测结果选定——单品种在场约 30%、最大回撤 −17%、每年约 13 次入场），或环境变量 `MARKETMIND_ALERT_TREND_SOURCE`。可选 `daily_state_machine`（精简版优先，否则全池）、`daily_state_machine:lean`、`daily_state_machine:full`、`daily_state_machine:six`，或 `包.模块:工厂函数`——任何返回带 `name` 和 `read(日期) -> TrendReading` 的对象的无参函数。月度规则已回测、未通过预注册标准，不接入（`docs/TREND_BACKTEST_MONTHLY_2026-09-29.md`）。顾问多数反对（vetoed）时照常推送并附否决标记（所有人 2026-09-29 决定）。
- 投票参数（窗口 5 天、持有期门槛 10、支持门槛）都在同一个文件里。

## 实现说明（2026-09-29，红队修复）

- （历史，已被下文 2026-09-29 改版取代）**观察模式持续到顾问能满足条件 A 为止**（`alerts/runner.py::load_advisors`、`can_satisfy_a`）：原实现只要 `data/advisors.json` 里有 1 个顾问就切到正式模式、只让顾问投票，而条件 A 需要至少 3 个顾问、来自至少 2 个组，于是在凑齐 3 个跨组顾问之前警报完全沉默。现在顾问人数 ≥ `MIN_ADVISORS` 且组数 ≥ `MIN_GROUPS` 才转为正式模式（只有顾问投票、推送手机）；否则继续用全部在册影子做观察模式（不推送），日志说明原因。
- 发现但未修改（超出本次范围）：`load_advisors` 只从长期名册取组别，`advisor_votes` 也只统计 `source_type = shadow` 的记录，所以晋升为顾问的 Playground 候选既不计入模式判断，也不参与投票。**已由 2026-09-29 改版解决**：Playground 顾问计入投票者名单并参与投票（组别 `playground`）。
- 2026-09-29 改版后，模式由所有人开关决定（见上），`can_satisfy_a` 已删除。
